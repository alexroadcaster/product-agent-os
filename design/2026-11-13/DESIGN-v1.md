# Product-Agent OS — desktop-дизайн и UI/UX

Source status: project-authored design proposal; текущие исходники и снимок владельца; публичные первичные страницы изучены 13.11.2026. Макеты содержат демонстрационные данные. Внедрение в приложение и приёмка владельцем не выполнены.

## Решение и границы

Предлагается полный пересмотр визуальной системы и компоновки desktop-интерфейса. Основное направление — **A / Cobalt Desk**: светлая рабочая среда, компактные списки, ясная типографика, синий акцент, панель выбранного объекта. **B / Graphite Mint** — альтернативная тёмная среда с деревьями и связями. **C / Warm Studio** — тёплая светлая среда с доской и цветными пиктограммами. Это три предложения для выбора, а не три утверждённые темы продукта.

Меняем представление, плотность, навигационную группировку, раскрытие полей, компоненты, визуальные состояния и движение. Сохраняем возможности, данные, роли, разрешения, workflow IDs/категории, API, подтверждения, сохранение черновиков, обработчики и правила переходов. Новые платежи, аналитика, метрики эффективности, совместная работа, AI-возможности и мобильная версия не входят в задачу. Существующие narrow-width/a11y гарантии при последующем внедрении нельзя ухудшить; отдельный mobile-дизайн не создаётся.

**Статус:** `needs_user_acceptance` для направления; реализация UI ещё `planned`. Этот документ не делает тему locked до выбора владельца. Для дизайна разрешены локальные эскизы; публикация, установка библиотек и изменение работающего сервиса не выполнялись.

## Аудит текущего интерфейса

Аудит проведён по исходникам и присланному снимку. Сервис владельца не подключался к тестовому клиенту, его данные не изменялись. Измерения текущего браузерного overflow не выполнялись, поэтому ниже разделены факт и гипотеза.

| Наблюдение | Основание | Последствие | Решение |
| --- | --- | --- | --- |
| Настройки совмещают общие параметры, подключение, большой workflow editor, миграцию, выполнение и очередь | `apps/web/src/ui/App.tsx`, `features/tasks/Settings.tsx`, `features/workflows/WorkflowManager.tsx`; снимок | Нет одного рабочего контекста; поиск нужного блока требует длинной прокрутки | Локальная навигация настроек; отдельные подэкраны процессов и выполнения |
| Все переходы раскрыты одновременно | `WorkflowManager.tsx:42–55`; на снимке 23 перехода | Одинаковые поля многократно повторяются | Список переходов слева, форма выбранного справа; исходные поля доступны полностью |
| Большие прямоугольные кнопки, одинаковая выразительность контейнеров | Снимок и `design/app.css` | Вторичные и опасные действия конкурируют с основными | Один основной акцент; текстовые/контурные вторичные кнопки; опасные действия в отдельном разделе |
| Доска имеет широкие колонки и локальный overflow | `app.css:21,31–35`, `TaskManager.tsx:71` | Семь колонок не помещаются вместе с деталями | Список по умолчанию; доска в своём viewport, свёрнутые пустые группы; при открытии деталей уменьшается число видимых колонок, а не расширяется документ |
| Детали имеют 8 вкладок | `TaskManager.tsx` | Горизонтальная цепочка навигации становится длинной | Основные вкладки и меню «Ещё», активная скрытая вкладка выводится в видимую позицию |
| Фиксированные минимумы task/session колонок | `app.css:378–384,445–448` | Возможный источник переполнения при вложенных панелях | Сначала измерить каждый экран; `minmax(0,1fr)`, `min-width:0`, адаптация по ширине контейнера |
| Визуальная навигация в основном текстовая | `App.tsx:77–92` и снимок | Разделы хуже различаются при быстром просмотре | Единый набор SVG + подписи, группировка по рабочей задаче |

Уже есть полезные основы: theme tokens, `:focus-visible`, skip link, `aria-current`, keyboard tabs, переносы, responsive breakpoints, `prefers-reduced-motion`. Их сохраняем. CSS содержит защиту от переполнения, поэтому утверждение «причина всех случаев найдена» было бы неверным. Первая задача внедрения — воспроизводимая инвентаризация каждого проблемного viewport и состояния.

| [Flaticon](https://www.flaticon.com/) | Каталог interface/animated icons и наборов | Направление для цветных пиктограмм одного семейства; отдельные пустые состояния | Смесь разных авторских стилей и растровые иконки в навигации |

Рекомендация — использовать обычный DOM/CSS/SVG для основной среды. Это следует из характера данных и доступности: формы, списки, дискретные состояния и статические связи не требуют 3D. Цель — современная выразительная рабочая среда, где действие и результат понятны с первого взгляда.

Выбор представления не обязан зависеть от темы в продукте: после выбора стиля список и доска остаются доступны в любой теме. В альбоме различие намеренно усилено для сравнения. Финальная A может использовать тёмную пару B, но это отдельное согласованное решение, а не обязательное удвоение объёма.

### Hallmark и UI/UX Pro Max: принятые решения

Hallmark применяется в `scope: app`, `redesign: full`, жанр `modern-minimal`: без hero, маркетинговых блоков и лимита слов для рабочей таблицы. Из theme deal получены Coral, Console, Vantage; использованы только принципы спокойных поверхностей и различимости состояний. Палитры и композиции разработаны для запрошенного набора вариантов, а не объявлены точным воспроизведением каталоговых тем. Текущие формы и их смысл сохраняются. Реальные материалы — название продукта, текущие разделы, поля и контракты; отсутствующие метрики/отзывы не добавлены.

UI/UX Pro Max `--design-system` и поиск `animation accessibility z-index loading` выполнены. Поисковая база предложила mobile/landing-паттерны; они отклонены как неподходящие desktop-инструменту. Использованы принципы контраста, progressive disclosure, keyboard navigation, reduced motion и смысловой обратной связи. Не переносим React Native, bottom tabs и mobile-first как требования этой задачи.

## Информационная архитектура

Сохраняются все 14 назначений. Изменение группировки не меняет область прав или проектный контекст.

| Группа боковой навигации | Разделы | Назначение |
| --- | --- | --- |
| Работа | Обзор, Задачи, Сессии | Что делать и что сейчас происходит |
| Ресурсы проекта | Агенты, Скиллы, Карта проекта, Документы, Проверки | Чем пользоваться и на какие источники опираться |
| Управление | Автономность, Решения | Какие ограничения действуют и что требует решения |
| Служебное | Поиск, Импорт, Резервная копия, Настройки | Обслуживание рабочей среды |

Верхняя строка: текущий проект, путь/раздел, реальное состояние подключения, действие обновления. Поиск можно поднять в header как второй вход в существующий раздел; нельзя подменять его новым глобальным поисковым API. Системные shortcut не перехватываются.

Внутри настроек: «Общие», «Проекты», «Подключение», «Процессы», «Выполнение», «Локальный сервис». Длинная форма перестаёт быть общим полотном. Это локальные панели существующего маршрута; никаких новых серверных операций. При переключении сохраняется существующий черновик. Грязная форма не очищается из-за unmount: сохраняем существующий registry либо оставляем owning component mounted.

## Экраны и поведение

| Экран | Компоновка | Основное взаимодействие | Сохраняемые ограничения |
| --- | --- | --- | --- |
| Обзор | Краткий контекст проекта, требующие внимания записи, последние существующие события | Переход к задаче/решению/сессии | Только данные существующего snapshot; без придуманных KPI |
| Задачи | Toolbar, список или доска, выбранный объект справа | Выбор строки показывает детали; закрытие возвращает focus/позицию; существующий переход статуса через свой preview | Все фильтры, архив, типы, WIP, связи, revisions, критерии, права и подтверждения |
| Детали задачи | Название, status, основные поля; вкладки «Описание», «Критерии», «История», «Ещё» | «Ещё» содержит файлы, комментарии, вложения, связи, сессии; все 8 исходных вкладок достижимы | Сохранение и preview сохраняют контракт, черновики не теряются |
| Сессии | Компактный каталог; центральная переписка; инспектор контекста по запросу | Выбор сессии; чтение событий; текущие Send/Stop/confirmation на прежних условиях | Нельзя показывать «остановлено» до ACK; stale и disconnected различимы |
| Агенты | Список ролей, профиль в соседней области, capabilities в раскрытии | Выбрать и изучить существующий профиль | Роль не означает активированный runtime; никаких новых прав |
| Скиллы | Каталог с метаданными, детальная область источника | Поиск/выбор/существующая генерация через текущий маршрут | Proposal и активный источник различаются |
| Карта проекта | Toolbar, подписанный граф, раскрываемый inspector, список-альтернатива | Выбрать узел, открыть исходник, раскрыть соседей | Static lexical связи; stale, unresolved и лимиты данных видимы |
| Документы | Каталог + reader с ограниченной длиной строки | Найти, открыть, перейти к источнику | Staged proposal, source и generated evidence не смешиваются |
| Проверки | Строки результатов, фильтры, подробности прогона | Открыть конкретный receipt | Успех проверки не равен приёмке или готовности к выпуску |
| Автономность | Текущая политика, объяснение области, отдельная форма изменения | Настроить существующие значения | Не менять default, admission и owner gates |
| Решения | Очередь вопросов и detail с контекстом, scope, diff/evidence | Прочитать, выбрать существующий вариант ответа | Expiry, revision, duplicate response и полномочия сохраняются |
| Поиск | Строка запроса, выдача, preview результата | Перейти к объекту с сохранением контекста | Только текущие источники и поддержанные типы |
| Импорт | Источник → preview → существующее подтверждение | Проверить до применения | Не добавить auto-apply и не скрыть конфликты |
| Резервная копия | Список/операции отдельно от восстановления | Выбрать и проверить доступное действие | Подтверждения восстановления и существующий authority reset сохраняются |
| Общие настройки | Короткие строки «Язык», «Тема», одна группа Save | Изменить и сохранить | Только прежняя система preferences |
| Проекты | Список + компактная форма добавления | Native folder picker, затем explicit Add | Cancel ничего не создаёт; scan по текущему контракту |
| Подключение | Способ, крупный текстовый статус, одно рекомендуемое действие, details | Подготовленный запрос, открытие Codex App, инструкция Send, ожидание подтверждения | Открытие App не равно подключению; не делать auto-send или fake success |
| Процессы | Выбор процесса/версии; подпанели «Состояния», «Переходы», «Назначения», «Recipes», «Версии», «Миграция» | Выбрать переход; изменить один объект; Save draft → Validate → Preview | Публикация только через текущий подтверждаемый путь; pinned версии неизменны |
| Выполнение | Форма перехода/цепочки отдельно от истории и очереди | Выбрать задачу, переход, режим, причину, preview | Manual не запускает agent; WIP/Stop/ACK и очередь прежние |
| Локальный сервис | Изолированный короткий danger-раздел | Явный checkbox и Quit | Не превращать в декоративную иконку питания без подтверждения |

### Три ключевых сценария

**Работа с задачей.** Пользователь открывает список, находит задачу, выбирает её. Справа показываются описание и критерии; список остаётся видимым. Полное редактирование использует текущий editor. Если места недостаточно, detail занимает область контента, а «Назад к списку» восстанавливает выбор и scroll. Переход статуса показывает существующие требования; анимация не означает, что операция уже успешна.

**Изменение процесса.** Пользователь выбирает процесс и версию, затем вкладку переходов. В каждой строке видны исходное/целевое состояние, право исполнения и наличие проверок. Справа редактируется только выбранный переход. Основные поля показываются сразу; required fields, check IDs, recipeId, success/failure state и user decision — в подписанной расширенной группе. Ошибка раскрывает нужную группу и фокусирует поле. Внизу формы закреплены Save draft и Validate; publish и migration вынесены в собственный review-контекст с текущими подтверждениями.

**Подключение.** Пользователь видит способ соединения и текущую стадию, затем нужное действие. Технические поля доступны в details. Ожидание агента — нейтральное состояние с пояснением; ошибка — причина и существующее восстановительное действие. Рядом нет большой карточки завершения сервиса. Имена стадий и доступность кнопок привязаны к реальным состояниям, не к таймеру анимации.

## Плотность, типографика и геометрия

- Desktop контрольные размеры: 1280×800, 1440×900, 1920×1080; дополнительно 1024px как узкое окно desktop. Масштабирование браузера 125%, 150%, 200% входит в будущую проверку.
- Рабочий контейнер до 1680px, центрирован на широком экране. Sidebar 216–232px, header 52–56px, gutters 20–24px. Основной контент — `minmax(0,1fr)`; ширина inspector ориентировочно 360–440px при достаточном месте.
- Текст описания 16px/1.5; compact labels и таблицы 14px/1.4; вторичные метаданные 12–13px только там, где не являются основным содержанием; заголовки 22–28px. Строка текста документа ограничена примерно 70–80 символами.
- Основная гарнитура — существующий `system-ui, Segoe UI, sans-serif`; допускается локально поставляемый шрифт с кириллицей после лицензии/проверки. Mono только для ID, кода и точных технических значений.
- Шаги расстояний 4/8/12/16/24/32px. Controls 36–40px; hit area до 44px без перекрытия соседей, coarse pointer 48px. Row 44–48px, при многострочном названии растёт.
- Радиусы: controls 6–8px, панели 10–12px. Поверхности разделяет тонкая граница или смена уровня; не оборачивать каждую строку в карточку внутри карточки.
- Иконки 18px navigation, 16px metadata, 20px action. Набор единый, stroke примерно 1.75–2px. Лейбл сохраняется; tooltip не заменяет доступное имя.
- Цветовые значения и fonts только в theme tokens; компоненты используют semantic roles. Фокус, ошибка, предупреждение, успех, выбор и данные — отдельные роли. Палитра не подменяет семантику.

### Контракт отсутствия горизонтального переполнения

Корень страницы не прокручивается горизонтально. Это проверяется по `scrollWidth <= clientWidth + 1`, а не только `overflow-x: clip`. Clip — последняя защита границы, не способ скрыть потерянные controls. У каждого flex/grid child есть допустимое сжатие; длинные пути/ID переносятся или раскрываются целиком. `100vw` внутри shell не используется.

Локальная горизонтальная прокрутка допустима только для явно двумерных данных: широкой доски, графа, большой таблицы или кода. У региона есть имя, keyboard-доступ, видимая граница и вертикальная/списковая альтернатива. При открытии объекта ширина страницы не растёт. Для тесного контейнера inspector заменяет область деталей или открывается как корректный dialog; не сжимать три панели до нечитаемых полос. Вкладки объекта используют «Ещё» или второй логичный уровень, не бесконечную горизонтальную полосу.

## Движение и обратная связь

| Событие | Предлагаемое движение | Длительность | Reduced motion |
| --- | --- | --- | --- |
| Hover/press кнопки | Небольшая смена визуального состояния без смещения layout | 100–140ms; focus мгновенно | Мгновенное состояние |
| Выбор вкладки | Подчёркивание/маркер через transform, контент коротким opacity | 140–180ms | Мгновенный выбор |
| Открытие inspector | translateX 8–12px + opacity; место в grid выделяется без анимации width | 180–220ms; выход 120–160ms | Без сдвига, сразу видимый контент |
| Смена раздела | Короткий crossfade только контентной области | 120–160ms | Без перехода |
| Раскрытие формы | Поля появляются сразу; допускается opacity | До 120ms | Сразу; focus остаётся корректным |
| Подтверждённое сохранение | Spinner заменяется check + текст; ширина кнопки постоянна | 140ms | Текстовое состояние |
| Обновление записи | Подсветка конкретной строки | 180ms | Стабильный маркер обновления |
| Наведение на граф | Выделение выбранного узла/соседей | 100–150ms | Сразу; то же при keyboard focus |

Нет `transition: all`, анимации `width/height/top/left`, бесконечных пульсаций статусных точек, parallax и заставок перед данными. Анимации прерываемы, не задерживают ввод, не создают искусственное ожидание. Порядок событий, длительность работы и статус выполнения берутся из данных. Skeleton только при настоящей загрузке; неизвестное время не изображается progress bar с выдуманным процентом.

## Состояния и доступность

Каждый data-region имеет full/loading/empty/error; при наличии источника также stale/partial/disconnected. Empty отличается от «ничего не найдено по фильтру». Stale сохраняет последнее содержимое с предупреждением и его provenance. Отсутствующие значения показываются «Нет данных», а не нулём.

Для interactive controls проектируются default, hover, focus-visible, pressed, selected, disabled, loading и error, когда применимо. Disabled сопровождается доступной причиной вне самого disabled tooltip. Ошибка формы стоит рядом с полем, общий summary ведёт к проблемам. Success не означает human acceptance. Toast не крадёт focus; важные ошибки не исчезают сами.

Требования: контраст основного и вторичного читаемого текста ≥4.5:1; крупного текста/UI-границ/значимых графических элементов ≥3:1 по применимым критериям; status различим по тексту/иконке. Tab/Shift+Tab логичны; modal trap и возврат focus проверяются; Escape закрывает только верхнюю отменяемую поверхность. Открытие панелей не теряет выделенную задачу. Длинные русские подписи, англоязычная локаль, пути и multiline content входят в проверку. Keyboard и screen-reader путь не заменяется drag-and-drop.

## Визуализация данных

| Задача пользователя | Представление и данные | Взаимодействие | Fallback и честность |
| --- | --- | --- | --- |
| Найти и сравнить задачи | Таблица существующих title/status/priority/owner | Выбор, текущие фильтры/группировка | Вертикальный список; не вводить новые поля |
| Понять распределение по состояниям | Доска существующих status groups | Выбор карточки, существующий move flow | Список; пустые состояния раскрываемы; все статусы доступны |
| Понять вложенность | Tree из существующих parent ID | Раскрытие ветки, переход к объекту | Плоский список с parent label; дерево не равно dependency graph |
| Понять переходы процесса | State diagram из definitions | Выбор перехода открывает ту же форму | Список from/to + checks; граф не разрешает обход validation |
| Читать ход сессии | Вертикальный журнал реальных событий | Выбор события/контекста | Текстовый chronological list; интервалы не выдаются за измеренное время |
| Исследовать исходники | GraphExplorer nodes/edges с типом связи | Выбор, соседи, source action | Список/inspector, stale/unresolved; lexical не runtime |

Основной renderer — DOM/SVG, текущие компоненты сначала. Не добавляем Recharts/ECharts/D3/WebGL без измеренной потребности. Планируем отрисовку видимой выборки; оптимизация/виртуализация только после профиля. Выбор, фильтры, scroll и возвращение сохраняются в уже поддержанном state/route-контракте; глобальная миграция URL или persistence не входит автоматически в редизайн.

Specialist pass: Build Web Data Visualization → visualization-strategy-and-critique; аналитические задачи — comparison, hierarchy, software structure, monitoring. Владелец смысловой схемы — текущий источник данных, владелец представления — UI slice. QA каждого слоя проверяет соответствие меток/узлов/связей данным, keyboard-path, still/reduced-motion и отсутствие скрытых обязательных действий. В этом этапе — local design review; доказательства runtime-улучшения отсутствуют.

Если изменение требует такого файла, это сигнал остановить конкретный slice и отдельно согласовать функциональное расширение.

## Приёмка будущего редизайна

1. Все 14 назначений и 8 вкладок задачи достижимы; нет потерянных controls/полей/действий. Матрица before/after связывает каждое с источником и тестом.
2. В 1280/1440/1920px на основных экранах нет page overflow, перекрытий, обрезанных кнопок и необходимости прокрутить весь документ по горизонтали. Разрешённые data-regions описаны отдельно.
3. Workflow сохраняет все состояния, transitions, recipes, assignments, версии, preview/validate/publish/migration gates. Процесс не меняется от его визуального переименования.
4. Несохранённый черновик, фильтр, выделение и scroll не теряются при открытии/закрытии деталей и навигации.
5. Контраст, keyboard-only, focus, zoom, RU/EN, reduced motion и loading/empty/error/stale проверены на текущем build.
6. В существующих task/session/workflow сценариях API payloads, revisions, permissions и реальный порядок подтверждений эквивалентны baseline. Stop/ACK, native approvals и опасные действия не упрощены.
7. Владелец проходит три сценария: найти/открыть задачу, изменить один переход в черновике, понять состояние подключения. Сравниваются ошибки, лишние действия и субъективная ясность; улучшение скорости не заявляется без измерения.
8. Будущие обязательные команды: `npm run check:web-m1`, `npm run build:web`, `node --test tests/web/*.test.mts`, применимые synthetic browser/accessibility сценарии из `TEST.md`. Эти проверки продукта не запускались как доказательство этого дизайн-этапа.

## Риски, откат и открытые решения

Основной риск — потерять смысл при уплотнении: спрятать блокировку, смешать статус с результатом, убрать нужное поле, потерять draft при переключении. Снижение риска: сначала parity map, затем UI wrappers, затем сценарная регрессия. Второй риск — сборная солянка компонентов; один token layer и одна семья icons обязательны. Третий — превратить схему в ложную аналитическую картину; data provenance и текстовый fallback сохраняются.

Откат последующей реализации — вернуть только изменения текущего UI slice по заранее сохранённому diff, без DB rollback и без разрушительных Git-команд. Текущий дизайн-пакет изолирован; его удаление/изменение не требуется для работы приложения.

Открыто для владельца: выбрать A/B/C либо комбинацию «A как основа + B как тёмная тема»; подтвердить комфортную плотность после просмотра макета; решить, нужен ли отдельный tree view задач уже в первой поставке. Все остальные UI-решения в документе — рабочее предложение. Дизайн можно согласовать сейчас, но внедрение требует отдельного запроса.
