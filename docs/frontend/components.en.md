## Documents and task backlinks — FUNC-02

In the current checkout `ArtifactExplorer.links(item)` reads `item.taskReferences` next to `taskIds`. A related-task button distinguishes matching revision, stale reference, revision unknown and source unavailable; navigation uses the ID of the already identified task. This describes the task-to-document relationship, not a document rename or automatic task-pin refresh. A document may have a current observed source while its task backlink remains stale.

Backend catalog/task-reference resolution reuse F28 normalization for `files`, `fileContexts`, structured `artifacts.reference` and legacy `artifactReferences`. Structured-only references participate in catalog `taskId` filtering and backlinks; external URLs are never interpreted as local paths. For a `workspace_file` document, `source.version` and legacy task `revision` pins are raw-byte SHA256, while `fileRevision` is a separate metadata/policy pin; entity revisions and `entity:N` sources retain their own semantics. Registry `rootIdentity` and `policyVersion` do not masquerade as content hashes. Full states/query boundaries are in [queries/impact](../code-intelligence/queries-impact.en.md#func-02--explicit-task-references-and-documents).

The reader keeps `available`/`stale`/`unavailable` separate from relationship states. A stale pin is not replaced with new content; missing/excluded/moved/deleted sources do not gain read authority merely because a task reference exists. Current registry root/policy own reading; sensitive paths/private-key data remain denied and permitted document display uses redaction. F02 does not launch graph providers, discovery, migrations or project files.
