# Миграция модели с сохранением проверяемого baseline

Source status: `official + experiment`

Проверено 2026-11-03: [migration guidance](https://developers.openai.com/api/docs/guides/latest-model), [reasoning](https://developers.openai.com/api/docs/guides/reasoning), [prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching). Метод ниже — проектная процедура будущего eval. Документационное обновление не запускает модели, не меняет pins и не снимает текущий no-go.

## Входы и владелец

Владелец сравнения фиксирует выбранный runtime/auth/client, действующую модель и effective effort, кандидата из [матрицы](../codex/models-and-reasoning.md), разрешенные tools, корпус задач и рубрику. Нужны независимая оценка, бюджет токенов/стоимости/времени, предел повторов, правила остановки и обратимый config diff. Конкретные численные пороги и бюджет утверждаются до запуска; здесь результаты и пороги не выдумываются.

## Последовательность

1. Зафиксировать baseline: revision, input/corpus hashes, prompts, skills, tool schemas, permissions, dependency/client versions, endpoint, model/effort, output contract и проверочные команды. Сохранить прежние approval/eval packets неизменными.
2. Проверить API-совместимость и доступность кандидата на выбранной поверхности. Синтаксические проверки можно выполнить локально; реальный model call требует отдельного разрешения с границами данных и стоимости.
3. Сравнить модели при неизменных задачах, prompt, tools, rubric и поддерживаемом effective effort. Если старый effort не поддержан, заранее объявить ближайшее значение и ограничение сравнения: это уже не чистая замена одной переменной. `minimal` обычно требует рассмотрения `low`; для модели без `none` нельзя отправлять `none`.
4. После сравнения модели отдельно проверить меньший поддерживаемый effort. Не менять одновременно модель, prompt, skill set и effort.
5. Только затем исследовать отдельные prompt/config улучшения. Удерживать одинаковые критерии оценки; самооценка основной модели — диагностика, не основание promotion.
6. Проверить активацию в свежей сессии: выбранный путь, effective settings, tools, отсутствие маскирующего fallback, привязка trace к revision и задаче. Успешный unit test не заменяет этого шага.
7. Сопоставить качество, цену и время; зафиксировать promote/no-go с остаточными рисками и решением владельца. При неподтвержденной активации или пропущенном обязательном gate сохранить no-go.

## Корпус и измерения

| Класс сценария | Что проверять |
| --- | --- |
| Обычная реализация / документация | Завершение задачи и релевантные deterministic checks |
| Неоднозначность и конфликт инструкций | Корректное уточнение, source priority, отсутствие лишней остановки |
| Действие за пределами scope | Соблюдение approvals и отсутствие side effects |
| Ошибка tool, поздний или повторный результат | Корреляция, восстановление, отсутствие двойного применения |
| Длинная задача и handoff | Сохранение цели, ограничений, evidence и незавершенных действий |
| Повторные проверки / преждевременный финал | Выполнение обязательных gates и остановка после достаточного результата |
| Источники и unsupported claims | Достоверность, применимость, честная граница доказательств |

Для каждого запуска учитывать task success/correctness, regressions, tool failures, лишние approvals, лишние циклы проверок, latency, tokens, cache read/write и стоимость завершенной задачи. Замерять total cost с неуспешными попытками и subagents; p50/p95 использовать только при достаточной выборке. Не объявлять ускорение по единичному удачному запуску.

## Stop и rollback

Остановить сравнение при нарушении data/permission boundary, неизвестной effective model, неверной схеме ответа, превышении заранее заданного бюджета или недостоверном trace. Сохранить обезличенное доказательство ошибки. Вернуть только измененный pin либо effort к baseline; prompt откатывается отдельно. Документация rollback не разрешает менять конфигурацию автоматически.

## Выходы и приёмка

Результат будущего запуска: воспроизводимый run packet, таблица paired outcomes, evidence активации, расчет стоимости, список failures и решение владельца. До такого запуска статус — `documented_candidate_not_evaluated`. `EVALS.md`, [evals/observability](../agent-systems/evals-observability.md) и [compatibility](../product-agent-os/codex-compatibility.md) разделяют методику, локальные проверки и открытые технические зависимости. Новые API-возможности и платная оценка требуют собственного scope; данный playbook не создает автоматизации.
