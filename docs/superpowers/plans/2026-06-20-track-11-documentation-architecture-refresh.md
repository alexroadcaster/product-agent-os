### Batch 44 Design Principles

- Manual-first: the first implementation must be `--dry-run` / `--stage`, not a daemon.
- Due-check is not execution: a weekly check may say a run is due, but cannot run the loop unless an approved command or automation invokes it.
- Product-Agent OS project scope only: session and feedback analysis is eligible only for workspaces with explicit Product-Agent OS evidence such as `.codex/product-agent-os/`, a Product-Agent OS config/skill/plan artifact or an owner-approved scope marker; unrelated user sessions and hidden app telemetry are out of scope.
- User satisfaction is evidence: owner feedback, revision acceptance, usefulness and user effort are stronger than an assistant saying `done`.
- Privacy first: no raw private chat logs, raw Codex transcripts, secrets, credentials, customer data or unredacted PII in ledgers, fixtures, reports or memory.
- Append-only metrics: baseline/current/candidate versions, score deltas, confidence intervals and accepted gaps must be recorded before comparing improvement or regression.
- Progress is a project artifact: every approved run must persist resumable progress state and render a project-local offline HTML artifact that displays due status, run progress, metric deltas, blockers and owner-review state; generated HTML remains orientation evidence, not proof by itself.
- Candidate-only modernization: skill/prompt/routing/hook/automation changes are proposals until owner approval, rollback target and verification evidence exist.
- Separation of roles: collection, reflection, judging and approval must be distinct enough that the loop cannot silently approve its own changes.

### Batch 45 Design Principles

- `existing_capability_first`: search current project APIs, framework features, standard library and configuration paths before custom logic.
- `delete_or_reuse_before_add`: prefer deleting code, using existing behavior or composing a local abstraction before introducing new code.
- `negative_dependency_rule`: reject new dependencies unless native/project options are insufficient, lifecycle risk is acceptable, and supply-chain review is recorded.
- `one_line_candidate_rule`: for small behavior, require the agent to name the simplest direct expression or framework call before writing a multi-line helper.
- `deep_module_over_shallow_module`: hide real complexity behind stable interfaces; do not create wrappers that merely rename calls.
- `comments_explain_why`: comments document intent, tradeoff, invariants and hazards; they do not narrate obvious statements.
- `legacy_seam_before_rewrite`: add characterization evidence and seam strategy before refactoring old or tangled code.
- `cleverness_budget`: clever code needs a measurable payoff, tests, naming clarity and review rationale.
