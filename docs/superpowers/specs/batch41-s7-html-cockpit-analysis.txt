## Key Problems

1. The renderer passes structural HTML tests while failing the user-facing artifact requirement. Current checks prove pages exist, are offline and avoid unsafe links/scripts; they do not prove readability, navigation, layout quality, or graph usefulness.
2. The artifact is split across 11 plain pages. That makes it hard to read as a project report, hard to compare sections, and unlike the cockpit references in `output/playwright/`.
3. There is no persistent navigation, no designed shell, no page state, no search/filter behavior and no selected-node/selected-file panel.
4. The renderer serializes packet data directly into tables and `<pre>` JSON blocks. This exposes implementation structure rather than explaining the project.
5. Graph support is not end-user graph support. The current Neural_Flow manifest has `graph_artifact_summary.status: not_available`, and the renderer has no visual node/edge projection even when graph data exists.
6. The existing `project_cockpit_model.py` and visual references are disconnected from `analysis_artifact_renderer.py`, so the implemented first-run path cannot produce the expected cockpit experience.
7. The report lacks two separate graph layers the owner expects: a file/source graph for the whole project and a code graph for entities, imports, tests, routes and hotspots when graph packets exist.
8. Long labels, tables and raw JSON overflow the viewport. The screenshots show default serif browser typography, wide tables, and content that is visually cut off or unreadable.
9. The visual QA gate is missing. There is no regression test that compares the artifact against the cockpit design direction, checks mobile/desktop layout, or blocks white-page regressions.
10. Product acceptance was too weak: "generated HTML exists" was treated as enough, even though the owner requirement is "a final user can understand the project from one artifact".

## Large Graph Rendering Policy

For projects above roughly 5,000 nodes and 50,000 edges, the cockpit must not render the full graph by default. The default view should show clustered overview, sampled or aggregated edges, selected-neighborhood subgraphs, query-driven expansion and bounded table fallback.

| Layer | Decision |
| --- | --- |
| Data model | Use a Graphology-compatible graph payload so the visual projection and query model stay separate from renderer choice. |
| Selected renderer | Use Cosmos.gl as the owner-selected graph visualization library for the cockpit graph canvas. |
| Selection reference | `https://cosmos.gl/?path=/docs/welcome-to-cosmos-gl--docs` |
| Primary renderer | Use locally bundled Cosmos.gl WebGL/GPU force graph rendering for interactive graph exploration, dense graph projection and large-project cockpit views. |
| Data adapter | Convert Product-Agent OS graph packets into Cosmos.gl typed arrays and index maps while preserving source-free metadata labels and generated-view-only boundaries. |
| Compatibility adapter | Keep Graphology-compatible payloads as the internal graph/query interchange format; Cosmos.gl is the selected visualization layer. |
| Secondary renderer | Sigma.js can remain only as a compatibility or fallback evaluation path, not the primary renderer. |
| Non-primary renderer | Cytoscape.js can be evaluated for smaller analysis or compound subgraphs, but should not be the primary 50k-edge cockpit renderer. |
| Fallback | Preserve static SVG/Canvas summary, cluster cards and bounded table fallback when WebGL or vendored assets are unavailable. |
| Dependency policy | No CDN, no network fetch and no install by default. Any vendored library requires version, license, hash and offline validation evidence. |
| Performance gates | 1k fixture uses Cosmos.gl interactive mode; 5k fixture uses clusters, hidden labels and edge sampling; 10k+ fixture stays responsive through LOD and fallback table; 50k-edge dense case validates link sampling, label suppression and no browser-freeze regression. |
