# PreToolUse при запуске B4

Source status: current repository source, observed tool decisions and independent static review. 19.11.2026.

## Вывод

Запись запуска `PAOS-PMETH-B4` содержала `brief_digest` с **66 шестнадцатеричными символами вместо 64**. `PreToolUse` разрешил изменение собственного маркера по штатному маршруту инициализации. Проверка формы нового JSON произошла при следующей команде, которая потребовала активный маркер. Точечное исправление дайджеста затем отклонила отдельная автоматическая проверка согласований. По указанию владельца реализация B4 остановлена.

## Как возникла блокировка

Закрытая задача больше не даёт полномочий на операции, требующие активного маркера. Флаг `--no-optional-locks` отсутствует в списке разрешённых литеральных форм `git`. В [конфигурации hook](../.codex/hooks.json#L17) указан matcher `Bash|apply_patch|Edit|Write`, запускающий `pre_tool_use_policy.py`. Для shell-команд классификатор признаёт чтением только известные имена, флаги и формы аргументов. `rg -A32`, сокращённый `rg -m`, `Get-FileHash` и команды с присваиваниями в данном вызове не проходят распознавание как чтение. Поэтому проверка маркера срабатывает и для некоторых команд чтения. Такое сообщение описывает маршрут классификации команды, а наличие записи следует проверять отдельно. ## Как восстановить работу

1. По отдельному решению возобновить B4 с новым корректным Task Start Brief и маркером её сеанса. Для нового сеанса использовать собственный маркер, выбранный SessionStart. Для возврата в текущем сеансе заранее согласовать штатную повторную инициализацию B4 с учётом предыдущего отказа автоматической проверки. Сохранить зафиксированную попытку B4 и закрытие B3. [Правила для нового объёма работы](../.codex/workflows/task-plan-lifecycle.md#session-isolation)
2. До записи вычислить SHA-256 стандартной библиотекой по зафиксированному допустимому представлению brief. Проверить полное соответствие `^sha256:[0-9a-f]{64}$`, разобрать полный JSON и сверить `session_id`, `task_id`, область работ и поля статуса. Внести только штатный патч собственного маркера и перечитать его. Затем проверить разрешённую операцию на одноразовой фикстуре в заявленной области.
3. Для исправления причины повторения сначала спроектировать и проверить валидацию **будущего** маркера до замены действующего. Поддерживаемый bootstrap должен получать и проверять полный кандидат. Обычный контекстный патч требует надёжного построения результата либо отдельной валидируемой операции. Частичный, неверный или неоднозначный кандидат должен оставлять прежний маркер на месте. Сохранить проверку текущего сеанса, точного пути, ограничений `report_authoring`, sandbox и отдельного согласования.

Проверка будущей правки должна включить переход закрытый B3 → валидный B4, длины 63/64/65/66, заглавные буквы, неверный JSON, чужой сеанс, смешанный патч, сохранность прежнего маркера при отказе и положительный и отрицательный прогоны в Codex на синтетических данных. Тесты bootstrap сейчас допускают неполные положительные фикстуры с отметкой о показанном brief. Их следует обновить при проверке полного кандидата. Правило распознавания команд чтения можно улучшать отдельным изменением с тестами для конкретных безопасных форм. [Тест bootstrap](../tests/product_agent_os/test_lifecycle_hooks.py#L453) · [Тест отчётного маршрута](../tests/product_agent_os/test_lifecycle_hooks.py#L95) · [Тест команд чтения](../tests/product_agent_os/test_lifecycle_hooks.py#L254)
