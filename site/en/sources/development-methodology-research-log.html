    Research Method¶

    Use the same protocol for each methodology or tool:

    1. Find a primary or official source.
    2. Extract five to ten verifiable claims without promoting community summaries to rules.
    3. Label each claim as official, methodology, tool convention, community or experiment.
    4. Map applicability to web/front-end, native/mobile, desktop, backend/API, data, AI/evals, docs and operations.
    5. Connect the claim to a Product-Agent OS template, workflow, skill, eval, discovery signal, docs page or staged CI proposal.
    6. Record failure modes: where the method is harmful, excessive or requires a human decision.
    7. Add a verification surface: test, eval gate, docs check, contract check, browser/runtime check or review checklist.

    Development Methodologies¶

    Methodology Short Description Primary Sources Product-Agent OS Signal
    Agentic / AI-native development SDLC work where Codex App, CLI, IDE extension, subagents and skills help plan, build, test, review and document changes while a human keeps ownership of architecture, product and quality. Codex build plugins, Agent Skills, Building an AI-Native Engineering Team, Codex AI app evals Require scoped inputs, ownership, tests/evals, source policy, approval policy, run evidence and the promotion path manual workflow -> skill -> plugin -> automation.
    Data-informed development Product decisions made through goals, signals, metrics, guardrails and post-release learning. Google HEART paper, Amplitude North Star Use metric specs, guardrail metrics, privacy notes and anti-Goodhart protection. Do not confuse it with Domain-Driven Design.
    Domain-Driven Design Modeling complex business logic around a domain model, ubiquitous language and bounded contexts. Martin Fowler: Domain-Driven Design, Bounded Context, Ubiquitous Language, Domain Language Apply only when domain complexity justifies it. Require a glossary, bounded contexts, aggregate/event choices only when useful, and explicit mapping to architecture boundaries.
    TDD Red-Green-Refactor loop: write a failing test, implement the smallest code that passes, then refactor with tests green. Agile Alliance TDD Require red -> green -> refactor evidence in RUNLOG or an explicit gap, especially for bug fixes and shared behavior.
    ATDD Acceptance tests written before implementation with product/customer, development and testing perspectives. Agile Alliance ATDD Connect REQUIREMENTS.md and TEST.md through acceptance scenarios before code changes.
    BDD Behavior scenarios and business outcomes expressed in a shared language for domain experts, testers and developers. Agile Alliance BDD Use for user behavior and business rules. It complements, but does not replace, unit/integration/contract tests.
    Feature-Sliced Design Frontend architecture methodology using layers, slices, segments, public API and import rules. Feature-Sliced Design documentation Treat as a strong default for growing UI apps, but do not force it onto backend/native/simple MVP work.
    Eval-driven AI development Repeatable eval suites for prompt/model/tool/RAG/agent behavior before changing production behavior. Codex AI app evals, OpenAI eval best practices Require a baseline, target path, no-secrets fixtures, assertions, run command and threshold.
    Docs-as-code Documentation lives with code, changes through review, and is built/checked as part of engineering workflow. GitLab documentation architecture, GitHub Actions workflows, GitHub protected branches Stage docs CI/CODEOWNERS proposals, but never enable external workflows without approval.

    Initial Gaps For Product-Agent OS¶

    Gap Why It Matters Research Action
    Conditional DDD, bounded context, ubiquitous language, FSD, metrics, evidence-before-completion, docs tooling and readiness statuses are now represented, but semantic sufficiency still needs owner review. Artifacts prove shape and traceability, not the correctness of domain terms, UI boundaries, metrics or evidence interpretation. Continue routing semantic sufficiency to owner review and accepted-gap records.
    ATDD/BDD need durable acceptance-scenario quality. Scenarios connect product requirements to test/eval-first work better than a generic checklist. Keep acceptance-scenarios.md and require product/development/testing review for important behavior.
    Docs tooling decisions need stack-aware routing. MkDocs, Docusaurus, Sphinx, Antora, Storybook, OpenAPI, DBML, Mermaid, PlantUML and Structurizr have different maintenance costs. Keep docs-tooling-decision.md and record present_unverified until commands run.
    Metrics need privacy and anti-Goodhart guardrails. One metric can distort behavior and telemetry can create privacy risk. Keep counter-metric, guardrail, qualitative review, retention and owner signoff fields.
    CI/CODEOWNERS/docs lint stay proposal-only. This preserves approval boundaries for external workflows and governance changes. Use explicit proposed_not_enabled or equivalent status in CI/governance templates.
