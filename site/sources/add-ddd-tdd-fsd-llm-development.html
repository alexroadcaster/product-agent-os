    ADD, DDD, TDD и FSD в разработке с LLM¶

    Source status: mixed source-backed draft
    Статус: входной исследовательский документ. Перед переносом claims в core guidance проверять первоисточники и явно отделять Data-Driven Development от Domain-Driven Design.

    Terminology boundary: этот draft использует DDD как incoming shorthand для Data-Driven Development. Product-Agent OS core methodology reserves DDD for Domain-Driven Design: domain language, bounded contexts, ubiquitous language, business rules, invariants и domain-to-architecture traceability. Когда этот draft referenced из Product-Agent OS docs или search results, treat Data-Driven Development как product/metric discipline и spell it out unless local team explicitly defines abbreviation.

    5. TDD — Test-Driven Development

    7. Ключевые отличия

    9. Как эти подходы сочетаются
    10. Применение в разработке с LLM

    14. Итоговая рекомендация
    15. Источники и полезные ссылки

    Краткое резюме¶

    Эти четыре подхода не являются прямыми конкурентами. Они отвечают на разные вопросы разработки:

    Data-driven development → что строить и почему это важно пользователю
FSD → где размещать код и как структурировать приложение
TDD → как доказать, что код работает правильно
ADD → как быстрее реализовывать задачи с помощью LLM-агентов

    Оптимальная связка для современной разработки с LLM:

    Data hypothesis
  → Feature slice
    → Acceptance tests
      → Agentic implementation
        → Human review
          → Metrics after release

    Для AI-приложений, semantic search, RAG, локальной индексации и работы с пользовательскими данными особенно важна связка:

    TDD + evaluation-driven testing + FSD + controlled ADD + DDD metrics

    Уточнение терминов¶

    Сокращение Расшифровка Смысл
    ADD Agentic-Driven Development / Agentic Coding Driven Development Разработка, где LLM-агенты помогают планировать, писать, тестировать, исправлять и документировать код.
    DDD (draft term here) Data-Driven Development Product and engineering decisions use data, metrics and feedback. Product-Agent OS core DDD means Domain-Driven Design; spell out Data-Driven Development in public guidance unless the local team explicitly defines abbreviation.
    TDD Test-Driven Development Подход, где сначала пишется тест, затем минимальная реализация, затем рефакторинг.
    FSD Feature-Sliced Design / Feature-Sliced Development Архитектурная методология организации frontend/UI-кода по слоям, фичам и бизнес-сущностям.

    Важно: термин FSD в реальной frontend-практике почти всегда означает Feature-Sliced Design, а не “Future Sliced Development”. Если используется выражение “Future Sliced Development”, его лучше уточнять, потому что оно не является распространённым стандартным термином.

    ADD — Agentic-Driven Development¶

    Суть¶

    ADD — это подход, при котором LLM-агент участвует в инженерном цикле не только как генератор кода, а как активный исполнитель задачи.

    Он может:

    • анализировать репозиторий;
    • строить план изменений;
    • писать код;
    • запускать тесты;
    • читать ошибки;
    • исправлять реализацию;
    • готовить diff или pull request;
    • писать документацию;
    • предлагать архитектурные улучшения.

    Человек при этом остаётся владельцем архитектуры, качества, безопасности и финального решения.

    Принцип работы ADD¶

    Типовой цикл:

    1. Goal / Intent
2. Specification / Критерии приемки
3. Agent Planning
4. Implementation Loop
5. Test Run
6. Error Fixing
7. Human Review
8. CI / Merge
9. Monitoring / Feedback

    1. Goal / Intent¶

    Человек формулирует задачу:

    Добавить импорт Telegram-экспорта.
Реализовать semantic search по сообщениям.
Добавить фильтр по чатам и периоду.
Переписать модуль индексации.

    2. Specification / Критерии приемки¶

    Задаются требования:

    - какие сценарии должны работать;
- какие edge cases важны;
- какие ограничения есть по архитектуре;
- какие тесты должны пройти;
- какие файлы нельзя менять;
- какие публичные API нельзя ломать.

    3. Agent Planning¶

    Агент изучает кодовую базу и предлагает:

    - какие модули затронуть;
- какие сущности создать;
- какие тесты добавить;
- где есть риски;
- какой план реализации.

    4. Implementation Loop¶

    Агент пишет код, запускает тесты, видит ошибки, исправляет код и повторяет цикл.

    5. Human Review¶

    Инженер проверяет:

    - архитектуру;
- безопасность;
- качество кода;
- обработку ошибок;
- зависимости;
- совместимость с проектом;
- отсутствие лишнего технического долга.

    Где ADD особенно полезен¶

    Задача Почему ADD подходит
    Boilerplate Агент быстро генерирует типовой код.
    CRUD Много повторяемых структур.
    UI-компоненты Можно быстро создавать формы, таблицы, модалки, состояния.
    DTO / schemas / adapters Хорошо формализуется.
    Тесты Агент может быстро покрыть сценарии.
    Рефакторинг Агент может менять много файлов по шаблону.
    Документация Хорошо подходит для объяснения API и модулей.
    Миграции Может автоматизировать механические изменения.

    Главные риски ADD¶

    Риск Описание
    Уверенно неверный код Агент может написать правдоподобную, но неправильную реализацию.
    Архитектурный шум Агент может создавать лишние абстракции и helper-файлы.
    Security bugs Особенно опасно в auth, payments, storage, permissions, encryption.
    Hidden coupling Код может работать локально, но ухудшать структуру проекта.
    Потеря контроля Если человек не ревьюит diff, агент начинает управлять архитектурой вместо команды.

    Критическая оценка¶

    ADD — мощный ускоритель разработки, но только при наличии:

    - понятной спецификации;
- тестов;
- архитектурных правил;
- code review;
- CI;
- ограничений на доступ к чувствительным частям проекта.

    Без этого ADD легко превращается в “быстрое производство технического долга”.

    DDD — Data-Driven Development (Draft Term)¶

    Суть¶

    In this draft, DDD means Data-Driven Development. Product-Agent OS core guidance should not use that abbreviation without disambiguation because its canonical DDD is Domain-Driven Design.

    Data-Driven Development — это подход, при котором решения о продукте, функциях, UX, качестве и приоритетах принимаются на основе данных.

    Данные могут включать:

    - продуктовую аналитику;
- поведение пользователей;
- retention;
- conversion;
- crash logs;
- performance metrics;
- search success rate;
- user feedback;
- A/B-тесты;
- cost metrics;
- support tickets;
- qualitative interviews.

    Принцип работы DDD¶

    1. Гипотеза
2. Метрики
3. Инструментация
4. Сбор данных
5. Анализ
6. Решение
7. Итерация

    1. Гипотеза¶

    Пример:

    Пользователи хотят быстро находить договорённости, задачи, даты и решения из старых переписок.

    2. Метрики¶

    Определяются показатели:

    - время до нахождения ответа;
- процент успешных поисков;
- количество уточняющих запросов;
- retention после первого импорта;
- latency поиска;
- стоимость одного LLM-ответа;
- процент ответов с подтверждением источниками.

    3. Инструментация¶

    В продукт добавляются:

    - события аналитики;
- performance logs;
- error logs;
- feedback buttons;
- privacy-aware telemetry;
- audit events;
- quality labels.

    4. Сбор данных¶

    Данные собираются из реального использования продукта.

    5. Анализ¶

    Команда смотрит:

    - где пользователи не находят ответ;
- какие импорты чаще всего падают;
- какие запросы дают нерелевантные результаты;
- где приложение тормозит;
- какие функции реально используются;
- какие функции игнорируются.

    6. Решение¶

    На основе анализа принимается продуктово-инженерное решение:

    - улучшить импорт;
- изменить UX поиска;
- добавить фильтры;
- поменять модель embedding;
- улучшить reranking;
- добавить подсказки запросов;
- убрать ненужную функцию.

    Где DDD особенно полезен¶

    Задача Почему DDD подходит
    Product discovery Помогает понять, что реально нужно пользователю.
    Приоритизация Снижает субъективность roadmap.
    UX-улучшения Видно, где пользователь застревает.
    AI quality Можно измерять релевантность, hallucination rate, groundedness.
    Performance Позволяет контролировать latency, RAM, CPU, cost.
    Growth Помогает понять, что влияет на retention и conversion.

    Главные риски DDD¶

    Риск Описание
    Goodhart’s Law Когда метрика становится целью, она перестаёт быть хорошей метрикой.
    Ложная точность Данные выглядят объективно, но могут быть собраны неправильно.
    Метрический фетишизм Команда начинает оптимизировать цифры вместо ценности.
    Игнорирование качественного контекста Не всё важное видно в метриках.
    Privacy issues Сбор данных может конфликтовать с приватностью пользователя.

    Критическая оценка¶

    DDD особенно полезен после появления первых пользователей и реального использования продукта.

    Но DDD не должен заменять:

    - стратегию;
- продуктовую интуицию;
- исследование пользователей;
- экспертную оценку;
- архитектурное мышление.

    Правильнее использовать DDD как feedback loop, а не как единственный способ принятия решений.

    TDD — Test-Driven Development¶

    Суть¶

    TDD — это подход, где тест пишется до реализации.

    Классический цикл:

    Red → Green → Refactor
    Этап Что происходит
    Red Пишется тест, который пока падает.
    Green Пишется минимальный код, чтобы тест прошёл.
    Refactor Код улучшается без изменения поведения.

    Принцип работы TDD¶

    1. Описать ожидаемое поведение в виде теста.
2. Убедиться, что тест падает.
3. Написать минимальную реализацию.
4. Убедиться, что тест проходит.
5. Улучшить структуру кода.
6. Повторить цикл.

    Пример¶

    Для функции semantic search:

    it("finds messages by semantic intent, not only exact keyword", async () => {
  const result = await searchMessages({
    query: "когда договорились встретиться?",
    chatIds: ["telegram_group_42"]
  });

  expect(result.items[0].text).toContain("встречаемся в пятницу");
  expect(result.items[0].chatId).toBe("telegram_group_42");
});

    Такой тест фиксирует поведение до реализации.

    Где TDD особенно полезен¶

    Задача Почему TDD подходит
    Парсеры Много edge cases.
    Импорт данных Нужно не потерять структуру и значения.
    API Поведение можно формализовать.
    Бизнес-логика Ошибки дорого стоят.
    Дедупликация Нужно чётко определить правила.
    Timezone logic Высокий риск скрытых багов.
    Permissions Ошибки могут быть критичными.
    Offline sync Много сложных сценариев.
    Search pipeline Нужны regression checks.

    Где TDD слабее¶

    Область Почему сложнее
    Чисто визуальный UI Сложно формализовать восприятие.
    Креативные задачи Нет одного правильного результата.
    LLM-ответы Выход вероятностный.
    Быстрые прототипы Тесты могут замедлить ранний поиск формы продукта.

    TDD для LLM-систем¶

    Для LLM-продуктов классического TDD недостаточно. Его нужно расширять до evaluation-driven testing.

    Нужны дополнительные проверки:

    Тип проверки Что проверяет
    Unit tests Парсеры, фильтры, форматтеры, splitters.
    Integration tests Связку importer → indexer → retriever → generator.
    Contract tests API, storage, модельные адаптеры.
    Golden dataset evals Качество ответов на фиксированном наборе запросов.
    Retrieval evals Recall@K, Precision@K, MRR, nDCG.
    Grounding checks Основан ли ответ на найденных источниках.
    Hallucination checks Нет ли утверждений без опоры на данные.
    Regression evals Не стало ли качество хуже после изменений.
    Cost tests Не выросла ли стоимость запроса.
    Latency tests Не ухудшилось ли время ответа.

    Критическая оценка¶

    TDD — один из лучших guardrails для разработки с LLM-агентами.

    LLM может писать код быстро, но именно тесты помогают определить:

    - что код должен делать;
- где границы поведения;
- что нельзя сломать;
- какие edge cases важны;
- где реализация регрессирует.

    Без тестов agentic development становится слишком рискованным.

    FSD — Feature-Sliced Design / Development¶

    Суть¶

    FSD — это методология архитектурной организации UI-кода по слоям, бизнес-срезам и сегментам.

    Она отвечает на вопрос:

    Где должен жить этот код?

    Вместо хаотичной структуры:

    components/
utils/
services/
hooks/
pages/

    FSD предлагает структуру, ориентированную на продуктовые смыслы:

    app/
pages/
widgets/
features/
entities/
shared/

    Основные элементы FSD¶

    Layers¶

    Слои приложения:

    Layer Назначение
    app Инициализация приложения, провайдеры, роутинг, глобальные стили.
    pages Страницы или экраны.
    widgets Крупные композиционные блоки интерфейса.
    features Пользовательские действия и бизнес-фичи.
    entities Бизнес-сущности: User, Chat, Message, Project.
    shared Общий переиспользуемый код без бизнес-смысла.

    Slices¶

    Срезы внутри слоя, обычно по бизнес-сущности или фиче:

    features/import-chat-history/
features/run-semantic-search/
entities/message/
entities/chat/
widgets/search-results/

    Segments¶

    Сегменты внутри slice:

    ui/
model/
api/
lib/
config/

    Пример структуры¶

    src/
  app/
    providers/
    routes/
    styles/

  pages/
    search-page/
      ui/
      model/

  widgets/
    chat-import-panel/
      ui/
      model/

    search-results/
      ui/
      model/

  features/
    import-chat-history/
      ui/
      model/
      api/
      lib/

    run-semantic-search/
      ui/
      model/
      api/
      lib/

  entities/
    message/
      model/
      api/
      lib/

    chat/
      model/
      api/
      lib/

  shared/
    ui/
    lib/
    api/
    config/

    Dependency rule¶

    Один из ключевых принципов FSD:

    Верхние слои могут импортировать нижние.
Нижние слои не должны импортировать верхние.

    Упрощённо:

    app
 ↓
pages
 ↓
widgets
 ↓
features
 ↓
entities
 ↓
shared

    Например:

    pages может импортировать widgets/features/entities/shared
features может импортировать entities/shared
entities может импортировать shared
shared не должен импортировать бизнес-слои

    Где FSD особенно полезен¶

    Ситуация Почему FSD подходит
    Большой frontend Упрощает навигацию и масштабирование.
    Много фич Каждая фича живёт в своём slice.
    Командная разработка Легче делить зоны ответственности.
    Частые изменения UX Изменения локализованы.
    LLM-assisted coding Агенту проще понимать структуру проекта.
    Web/mobile/desktop UI Можно использовать как архитектурный каркас интерфейса.

    Главные риски FSD¶

    Риск Описание
    Избыточность Для маленького MVP может быть слишком тяжеловесно.
    Споры о размещении Команда может тратить время на “куда положить файл”.
    Формальная имитация Можно создать папки FSD, но не соблюдать зависимости.
    Не покрывает backend целиком FSD — прежде всего про UI/frontend architecture.
    Порог входа Новым разработчикам нужно понимать layers/slices/segments.

    Критическая оценка¶

    FSD особенно хорош для продуктовых UI-приложений, где интерфейс быстро растёт.

    Но FSD не должен становиться самоцелью. Для небольшого MVP можно начать с упрощённой feature-based структуры и постепенно приблизиться к FSD по мере роста сложности.

    Ключевые отличия¶

    Критерий ADD DDD TDD FSD
    Главный вопрос Как быстрее и безопаснее реализовать с AI-агентом? Что реально нужно пользователю и бизнесу? Как доказать, что код работает? Где должен жить код?
    Основной драйвер LLM-агент + спецификация + ревью Данные, метрики, эксперименты Тесты и ожидаемое поведение Архитектурные границы

    Плюсы и минусы¶

    Концепция Плюсы Минусы
    ADD Сильно ускоряет реализацию; хорошо подходит для больших codebase; агент может писать тесты, рефакторить, запускать CLI; снижает ручной boilerplate. Требует строгого ревью; возможны hallucinated abstractions; риск security bugs; без тестов агент уверенно ломает код; senior-инженер нужен ещё сильнее.
    DDD Помогает строить нужные функции; улучшает приоритизацию; снижает риск “строим не то”; даёт feedback loop после релиза. Требует аналитики и инфраструктуры; плохие метрики ведут к плохим решениям; может тормозить радикальные идеи; privacy/compliance усложняются.
    TDD Даёт regression safety; улучшает дизайн интерфейсов; отлично работает с LLM-агентами; позволяет безопаснее рефакторить. Увеличивает стартовую стоимость; тесты могут быть хрупкими; плохо написанные тесты создают ложную уверенность; сложнее для UI и LLM-output.
    FSD Упрощает навигацию по UI-коду; снижает coupling; помогает команде и LLM понимать проект; хорошо масштабируется. Избыточен для маленьких MVP; требует дисциплины; возможны споры “куда положить файл”; не решает backend/domain architecture сам по себе.

    Как эти подходы сочетаются¶

    Эти подходы лучше рассматривать как разные уровни инженерной системы.

    DDD → выбрать правильную проблему
FSD → разложить решение по архитектуре
TDD → зафиксировать ожидаемое поведение
ADD → ускорить реализацию через LLM

    Практическая последовательность¶

    1. DDD: определить гипотезу и метрики.
2. FSD: определить feature slice и место кода.
3. TDD: написать тесты и критерии приёмки.
4. ADD: поручить LLM-агенту реализацию.
5. Review: проверить архитектуру, безопасность и diff.
6. CI: прогнать тесты, type-check, lint, evals.
7. DDD: измерить результат после релиза.

    Визуальная схема¶

    User problem
   ↓
Data hypothesis             ← DDD
   ↓
Feature boundary            ← FSD
   ↓
Executable specification    ← TDD
   ↓
Agentic implementation      ← ADD
   ↓
Human review + CI
   ↓
Release
   ↓
Metrics + feedback          ← DDD

    Применение в разработке с LLM¶

    ADD + LLM¶

    ADD — самый естественный подход для использования LLM.

    Что можно поручать LLM-агенту¶

    - создать компонент;
- реализовать API-клиент;
- написать тесты;
- сделать рефакторинг;
- добавить типы;
- обновить документацию;
- найти потенциальные баги;
- проанализировать codebase;
- подготовить pull request;
- сгенерировать миграции;
- сделать адаптер под новый провайдер.

    Что нельзя отдавать LLM без контроля¶

    - security-critical код;
- auth и permissions;
- платежи;
- шифрование;
- обработку персональных данных;
- сложную синхронизацию;
- конкурентность;
- storage engine;
- production migrations;
- критичную бизнес-логику без тестов.

    Пример промпта для ADD¶

    Ты работаешь в существующем TypeScript-проекте.

Задача: реализовать feature import-chat-history.

Правила:
- Сначала изучи структуру проекта.
- Используй Feature-Sliced Design.
- Не меняй публичные API без явного предложения.
- Сначала напиши тесты для happy path и edge cases.
- Затем реализуй минимальный код.
- Запусти тесты и исправь ошибки.
- В конце дай summary изменений и рисков.

    DDD + LLM¶

    LLM может помогать анализировать данные, но не должен быть единственным источником истины.

    Что LLM может делать¶

    - суммаризировать user feedback;
- кластеризовать жалобы;
- находить повторяющиеся pain points;
- анализировать логи;
- формулировать продуктовые гипотезы;
- предлагать метрики;
- объяснять аномалии;
- готовить отчёты по экспериментам;
- анализировать support tickets.

    Важное ограничение¶

    LLM может хорошо объяснять данные, но может ошибаться в интерпретации.

    Поэтому решения нужно принимать через связку:

    raw data → analysis → human interpretation → decision → experiment → measurement

    Метрики для AI-приложения¶

    Метрика Зачем нужна
    Search success rate Понять, находит ли пользователь нужную информацию.
    Time to answer Сколько времени занимает путь от запроса до результата.
    Top-K relevance Насколько релевантны первые результаты.
    Answer groundedness Основан ли ответ LLM на найденных сообщениях.
    Hallucination rate Частота ответов без опоры на данные.
    Import success rate Стабильность импорта переписок.
    Indexing latency Скорость построения индекса.
    Query latency Скорость ответа поиска.
    RAM/CPU usage Критично для desktop-приложения.
    Cost per answer Важно при использовании облачных моделей.
    User correction rate Как часто пользователь исправляет или уточняет запрос.

    TDD + LLM¶

    TDD — один из лучших способов управлять LLM-разработкой.

    Плохой запрос:

    Сделай импорт Telegram-чата.

    Хороший запрос:

    Сначала напиши тесты для импорта Telegram JSON:
1. валидный экспорт;
2. пустой файл;
3. сообщения без text;
4. сообщения с несколькими типами контента;
5. дедупликация;
6. сохранение senderId, chatId, timestamp;
7. обработка timezone.

Затем реализуй минимальный код, чтобы тесты прошли.
Не меняй публичный API без отдельного предложения.

    Почему это работает¶

    Тесты дают LLM:

    - ясную цель;
- проверяемый результат;
- ограничения;
- edge cases;
- сигнал об ошибках;
- защиту от регрессии.

    Для LLM/RAG-систем¶

    Нужно использовать не только unit tests, но и evals:

    - retrieval evals;
- answer quality evals;
- grounding checks;
- hallucination checks;
- regression datasets;
- latency thresholds;
- cost thresholds.

    FSD + LLM¶

    FSD помогает LLM не разбрасывать код хаотично.

    Почему это важно¶

    LLM лучше работает, когда структура проекта предсказуема.

    FSD даёт агенту правила:

    - не клади бизнес-логику в shared/ui;
- не импортируй features друг из друга напрямую;
- не размещай entity-specific код в pages;
- каждая feature имеет ui/model/api/lib;
- общие компоненты живут в shared/ui;
- бизнес-сущности живут в entities;
- страницы собирают widgets/features/entities, но не содержат сложную бизнес-логику.

    Пример системной инструкции для LLM-агента¶

    Архитектурные правила проекта:

- Используй Feature-Sliced Design.
- UI-компоненты фичи размещай в features/<feature>/ui.
- Состояние и бизнес-логику размещай в features/<feature>/model.
- API фичи размещай в features/<feature>/api, если он специфичен для фичи.
- Бизнес-сущности Message, Chat, Contact размещай в entities.
- Общие UI-компоненты размещай в shared/ui.
- Общие утилиты размещай в shared/lib.
- Pages только собирают widgets/features/entities.
- Не создавай cross-imports между slices одного слоя.
- Не создавай глобальный utils.ts без необходимости.

    Применение для web, mobile и desktop¶

    Web-приложения¶

    Для web лучше всего работает связка:

    FSD + TDD + ADD + DDD
    Задача Подход
    Структура React/Next/Vue/Svelte приложения FSD
    Реализация компонентов и страниц через LLM ADD
    Проверка бизнес-логики, API, hooks, stores TDD
    Проверка UX, retention, conversion, search behavior DDD
    Рефакторинг frontend-кода ADD + TDD
    Масштабирование UI FSD

    Практическая рекомендация для web¶

    - Для MVP можно начать с упрощённого FSD.
- Для проекта с несколькими фичами FSD стоит внедрить сразу.
- Для API, stores, reducers, hooks — использовать TDD.
- Для генерации UI и boilerplate — использовать ADD.
- После релиза измерять поведение через DDD.

    Mobile-приложения¶

    Для mobile лучше использовать:

    FSD-like feature architecture + TDD + DDD + controlled ADD
    Область Лучший подход
    Screens / flows / feature modules FSD-like structure
    Domain logic TDD
    Offline cache TDD
    Sync TDD + integration tests
    Permissions TDD + manual/security review
    Crash rate, retention, onboarding DDD
    Генерация UI, DTO, adapters ADD
    Storage, encryption, auth ADD только под строгим ревью

    Для React Native и Flutter¶

    FSD можно применять почти напрямую:

    app/
pages или screens/
widgets/
features/
entities/
shared/

    Для native Swift/Kotlin¶

    Лучше адаптировать идею:

    features/
core/
domain/
data/
presentation/
shared/

    Смысл тот же: фича должна быть локализована, а не размазана по проекту.

    Desktop-приложения¶

    Для desktop особенно важны:

    - локальное хранение;
- файловая система;
- privacy;
- производительность;
- индексация;
- offline-first логика;
- память и CPU;
- долгие фоновые операции.

    Рекомендуемая связка:

    FSD для UI
TDD для core/local logic
DDD для продуктовых и performance metrics
ADD для ускорения реализации
    Компонент Подход
    UI: импорт, поиск, настройки, результаты FSD
    Парсинг Telegram/WhatsApp/Slack/Discord экспортов TDD
    Дедупликация сообщений TDD
    Локальная индексация TDD + performance tests
    Semantic search / embeddings TDD + retrieval evals
    LLM answer generation Evaluation-driven testing
    CPU/RAM/GPU usage DDD через performance telemetry
    Приоритизация фич DDD
    Генерация boilerplate ADD
    Security/privacy Human review + tests

    Практическая рекомендация для desktop¶

    Для desktop-приложения анализа переписок TDD критически важен.

    Особенно для:

    - парсинга экспортов;
- дедупликации сообщений;
- корректной обработки дат и timezone;
- восстановления структуры чатов;
- маппинга пользователей;
- индексации;
- локального поиска;
- защиты приватных данных;
- очистки и удаления данных;
- миграций локальной БД.

    Ошибки в этих местах могут разрушить доверие к приложению.

    Практический workflow¶

    Рекомендуемый цикл разработки¶

    1. Product hypothesis
2. Metrics definition
3. Feature boundary
4. Test design
5. Agentic implementation
6. Review
7. CI/evals
8. Release
9. Measurement
10. Iteration

    Детально¶

    1. Product hypothesis¶

    Пользователь хочет находить полезную информацию в старых переписках быстрее, чем вручную.

    2. Metrics definition¶

    - search success rate;
- time to answer;
- top-5 relevance;
- import success rate;
- indexing time;
- query latency;
- RAM usage;
- hallucination rate;
- answer groundedness.

    3. Feature boundary¶

    features/run-semantic-search/
features/import-chat-history/
features/filter-search-results/
widgets/search-results/
entities/message/
entities/chat/

    4. Test design¶

    - unit tests for parser;
- integration tests for indexing;
- retrieval tests for search;
- golden dataset tests for answer generation;
- performance tests for indexing and query latency.

    5. Agentic implementation¶

    LLM-агент реализует изменения строго по правилам проекта.

    6. Review¶

    Человек проверяет:

    - diff;
- архитектуру;
- edge cases;
- безопасность;
- читаемость;
- зависимости;
- покрытие тестами.

    7. CI/evals¶

    - unit tests;
- integration tests;
- type-check;
- lint;
- e2e;
- retrieval evals;
- LLM answer evals;
- performance thresholds.

    8. Release¶

    Изменение попадает к пользователям.

    9. Measurement¶

    Смотрим реальные метрики и feedback.

    10. Iteration¶

    Делаем следующую итерацию на основе данных.

    Пример для приложения поиска по перепискам¶

    Фича: “Поиск договорённостей в чатах”¶

    DDD: гипотеза¶

    Пользователь хочет быстро находить договорённости, даты, задачи и решения из старых переписок.

    DDD: метрики¶

    - % успешных поисков;
- среднее время до найденного ответа;
- точность top-5 результатов;
- latency запроса;
- RAM usage при индексации;
- частота уточняющих запросов;
- количество ответов с источниками;
- частота жалоб на нерелевантность.

    FSD: структура¶

    src/
  pages/
    search-page/
      ui/
      model/

  widgets/
    search-results/
      ui/
      model/

    search-filters/
      ui/
      model/

  features/
    run-semantic-search/
      ui/
      model/
      api/
      lib/

    refine-search-query/
      ui/
      model/
      lib/

  entities/
    message/
      model/
      api/
      lib/

    chat/
      model/
      api/
      lib/

  shared/
    ui/
    lib/
    api/
    config/

    TDD: тесты¶

    - находит сообщение по смыслу, а не только по ключевому слову;
- фильтрует по периоду;
- фильтрует по конкретным чатам;
- корректно группирует результаты по чатам;
- не возвращает удалённые или скрытые сообщения;
- сохраняет ссылку на оригинальное сообщение;
- возвращает fallback, если ничего не найдено;
- не вызывает LLM, если retrieval не нашёл релевантных источников.

    ADD: задача агенту¶

    Реализуй feature run-semantic-search по FSD.

Требования:
- Сначала проверь существующие entities/message и entities/chat.
- Не создавай новые shared helpers без необходимости.
- Соблюдай dependency rule FSD.
- Сначала добавь unit/integration tests.
- Затем реализуй минимальный код.
- Добавь обработку пустых результатов.
- Ответ должен содержать references на найденные сообщения.
- Запусти тесты и исправь ошибки.
- В конце дай summary изменений и рисков.

    DDD после релиза¶

    Проверить:

    - пользователи чаще находят нужные сообщения?
- уменьшается ли время поиска?
- какие запросы не дают результата?
- где LLM галлюцинирует?
- какие мессенджеры дают больше ошибок импорта?
- какой этап наиболее медленный: импорт, индексация, retrieval или generation?

    Когда что лучше применять¶

    Ситуация Лучший выбор
    Быстрый прототип ADD + минимальный TDD
    MVP на 1–2 экрана Простая feature-структура, без полного FSD
    Большой web/mobile UI FSD
    Сложная бизнес-логика TDD
    AI/RAG/semantic search TDD + eval-driven testing + DDD
    Неясно, какую фичу делать DDD + qualitative discovery
    Много boilerplate ADD
    Работа с privacy/security TDD + human review; ADD только как помощник
    Команда растёт FSD + coding conventions + ADD rules
    Локальное desktop-приложение TDD для core, FSD для UI, DDD для performance/UX, ADD для ускорения

    Итоговая рекомендация¶

    Для modern mobile/web/desktop разработки с LLM оптимальная иерархия такая:

    1. DDD — выбрать правильную проблему и метрики.
2. FSD — задать архитектурные границы UI и фич.
3. TDD — зафиксировать ожидаемое поведение.
4. ADD — ускорить реализацию через LLM-агентов.

    Самая сильная комбинация:

    DDD tells you what matters.
FSD tells you where code belongs.
TDD tells you whether it works.
ADD helps you build it faster.

    Для приложения анализа переписок и semantic search особенно рекомендуется:

    TDD + retrieval evals + FSD + controlled ADD + DDD metrics

    Практический принцип¶

    Не просить LLM просто “сделай фичу”.

Лучше:
1. определить метрику и пользу;
2. определить архитектурный slice;
3. написать тесты и evals;
4. поручить агенту реализацию;
5. проверить diff;
6. измерить результат.

    Такой подход позволяет использовать LLM не как хаотичный генератор кода, а как управляемый инженерный инструмент.
