    Source status: official + verified methodology + implementation planning

    Дата: 2026-05-23.
    Основано на development methodology research log, gap matrix и текущем состоянии Product-Agent OS после Track 7. Дополнено сравнительным анализом obra/superpowers как community/opensource intake source для behavioral workflow design; этот источник is not source of truth для Codex и используется только для идей, которые проходят через Product-Agent OS safety, source и eval gates.

    Цель Track 8¶

    Сделать Product-Agent OS способным не просто генерировать control-plane artifacts, а выбирать и проверять инженерные методологии, стандарты и documentation tooling по контексту проекта:

    • методологии: Agentic / AI-native development, TDD, ATDD, BDD, DDD, FSD, data-informed development, eval-driven AI development, docs-as-code;
    • стандарты и specs: ADR/MADR, C4, arc42, OpenAPI, AsyncAPI, SemVer, Keep a Changelog, CODEOWNERS, GitHub Actions;
    • инструменты: Swagger/OpenAPI tooling, Storybook, Mermaid, PlantUML, Structurizr DSL, DBML/dbdocs/SchemaSpy, MkDocs, Docusaurus, Sphinx, Antora, Read the Docs, TypeDoc, JSDoc, Javadoc, C# XML docs, Vale, markdownlint.

    Applicability model¶

    Каждая методология, стандарт или tool должны получать не boolean present/missing, а один из статусов:

    Status Значение
    not_applicable Для текущего стека/масштаба/изменения не нужен.
    applicable_missing Нужен, но не найден; требуется staged proposal или explicit gap.
    present_unverified Найден, но команда проверки неизвестна или не запускалась.
    present_verified Найден и есть актуальная проверка/артефакт evidence.
    proposal_staged Подготовлено предложение, но оно не применено к проекту.
    approval_required Требуется approval: external write, CI activation, hosted docs, DB access, secrets-sensitive operation.
    explicit_gap_accepted Gap зафиксирован и принят владельцем как временное решение.

    Usage mode model¶

    usage_mode должен быть составным, потому что реальная задача часто пересекает несколько сценариев: например, bug rescue внутри complex system или security-sensitive API migration.

    Field Meaning
    primary Главный режим, определяющий first response and minimum artifacts.
    secondary Дополнительные режимы, которые добавляют gates без смены основного workflow.
    confidence low, medium, high; при low plugin должен задавать короткий уточняющий вопрос или выбирать safe fallback.
    reasons 2-5 фактов из workspace/user prompt, почему выбран режим.
    fallback Безопасный режим, если classification спорная, обычно standard_feature или maintenance.
    first_response_contract Что plugin сообщает или спрашивает на первом ходе: выбранный режим, evidence gap, approval boundary и next smallest action.
    minimum_artifacts Минимальный staged artifact set для режима; advanced proposals появляются только после необходимости или approval.
    behavioral_eval_cases Prompt/session fixtures, которые доказывают правильный route, stop condition и отсутствие forbidden behavior.
